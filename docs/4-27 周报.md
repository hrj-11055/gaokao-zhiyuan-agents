## 四、智能体设计评估与优化建议

### 现状评估

当前 Dify Agent 设计（v1.0）已完成基础架构：

- ✅ Workflow 节点设计（信息提取 → 意图路由 → 知识库检索 → 回答生成）
- ✅ 4 类意图路由（志愿/专业/院校/闲聊）
- ✅ 张雪峰人设 Prompt
- ✅ 20 题标准测试集 + 四维度评估体系
- ✅ 6 个知识库规划

### 存在的问题（5 个关键短板）

#### 问题 1：意图分类过于简单

**现状：** 只有 4 类（volunteer/major/school/chat），但真实用户提问往往是混合意图。

> 例："我580分想学计算机去哪个学校好" = 志愿 + 专业 + 院校 三合一

**优化方案：**

- 改为多标签分类（一条 query 可同时命中多个意图）
- 增加子意图：志愿→冲稳保/专业对比/地域选择
- 增加"综合咨询"类型，覆盖多意图混合场景

#### 问题 2：分数线数据用 RAG 检索效率低

**现状：** KB-2 录取分数线（31 省 × 3 年）作为 Markdown 文件上传知识库，用语义检索。

**问题：** 分数线是结构化表格数据（学校 + 省份 + 分数 + 位次），语义检索不擅长精确匹配数值。

> 用户问"广东 580 物理类能上什么学校"，RAG 可能检索不到最相关的分数线记录。

**优化方案：**

- **结构化数据走数据库查询，不走 RAG**
- 方案 A：在 Dify Workflow 中增加 HTTP 工具节点，调用自建 API 查询分数数据
- 方案 B：将分数线数据导入微信云数据库，云函数查询后注入 Prompt
- RAG 只负责非结构化知识（专业分析、院校评价、语料风格）

#### 问题 3：缺少会话状态持续管理

**现状：** 设计文档提到"最近 10 轮对话历史"，但没有用户画像跨轮积累机制。

**问题：** 用户可能在第 1 轮说省份，第 3 轮说分数，第 5 轮才说选科。当前设计中信息提取节点只看当前轮，容易丢失。

**优化方案：**

- 在 Workflow 中增加"用户画像合并"节点：每轮提取的信息追加到 session 变量中
- 用 Dify 的 conversation variable 功能存储累积画像
- 输入变量从"仅当前消息"改为"当前消息 + 累积画像"

#### 问题 4：知识库无分层检索

**现状：** 所有知识库平铺检索，839 个专业报告 + 31 个省份分数线 + 院校报告 = 数据量大。

**问题：** 全量检索噪音大，检索质量随数据量增长而下降。

**优化方案：**

- **分层检索：** 先根据意图 + 门类缩小范围，再精确检索
- 专业百科按学科门类分 6 个子知识库（人文/社科/理工/农医/管理/艺术）
- 分数线数据从知识库移出，走结构化查询
- 为每个 chunk 添加 metadata 标签（门类、省份、年份），利用 Dify 的 metadata filter

#### 问题 5：缺少回答质量验证环节

**现状：** LLM 生成回答后直接输出，没有事实性校验。

**问题：** AI 可能编造不存在的学校/专业/分数（幻觉），这是最严重的质量风险。

**优化方案：**

- 增加"生成 → 校验"两步流程
- 第一步 LLM 生成回答
- 第二步用规则校验：提到的学校是否在数据库中？引用的分数是否在知识库范围内？
- 校验不通过则重新生成或标注"仅供参考"

### 性能评估：大量数据下检索会不会慢？

**结论：短期不会，但需要注意数据组织方式。**

| 数据量级                     | 检索方式 | 预计延迟 | 是否有问题                          |
| ---------------------------- | -------- | -------- | ----------------------------------- |
| 839 条专业报告（~3MB）       | 向量检索 | 1-3 秒   | ✅ 无问题，向量库处理这个量级很轻松 |
| 31 省分数线（~1.5MB 纯文本） | 语义检索 | 2-5 秒   | ⚠️ 检索质量差（数值匹配不准）     |
| 120 所院校报告（~5MB）       | 向量检索 | 1-3 秒   | ✅ 无问题                           |
| 全部合计（~10MB）            | 混合检索 | 3-8 秒   | ⚠️ 噪音多，需要分层               |

**核心建议：**

1. **分数线走结构化查询**（数据库/API），不走 RAG — 这是最大的性能和质量提升点
2. **知识库按类型拆分**，每个知识库控制在 200 条以内
3. **Dify 的向量库（Weaviate）处理 10MB 数据没有性能问题**，瓶颈在于检索精度，不是速度
4. **真正影响用户体验的是 LLM 生成时间（3-8 秒）**，不是检索时间。用 SSE 流式输出缓解

## 七、事前验尸分析（Pre-mortem）

> 假设项目已经失败了，倒推可能的原因。聚焦于 **尚未纳入风险管理** 的盲区。

### 🔴 致命级（可能导致项目直接失败）

#### 1. 小程序 SSE 流式传输的技术坑

**问题：** 微信小程序 **不原生支持 SSE**（没有 EventSource）。Dify 的流式输出是标准 SSE 格式，不能直接用。

**现状：** 项目设计文档写的"SSE 流式输出"，实际上在小程序端需要用 `enableChunked` + 手动解析 ArrayBuffer 实现，复杂度远超预期。

**具体坑位：**
- `onChunkReceived` 返回的是原始 ArrayBuffer 二进制块，需自行 UTF-8 解码 + SSE 格式拆分
- 分块边界不可控：一个 SSE event 可能被拆成多个 chunk，或多个 event 合并一个 chunk
- 安卓端有 ~60 秒硬编码超时，与 Dify 长对话冲突
- iOS / Android / 开发者工具行为不一致
- 需要后端每 15-20s 发心跳保活（`: keepalive\n\n`）

**影响：** 如果低估这个复杂度，W3-W4 开发周期可能翻倍。

**建议：** W3 第一天先做一个 SSE → 小程序的最小原型，验证可行性后再铺开开发。

#### 2. AI 小程序审核门槛被低估

**问题：** 上线审核不是"提交 → 等几天"这么简单。微信对 AI 对话类小程序有 **硬性门槛**：

| 要求 | 说明 | 本项目现状 |
|------|------|-----------|
| **企业主体** | 个人主体不支持深度合成类目，直接被拒 | ❓ 是否已有企业主体？ |
| **算法备案** | 需要提供 DeepSeek 的算法备案证明截图 | ⬜ 未准备 |
| **深度合成类目** | 必须添加"深度合成 - AI问答"服务类目 | ⬜ 未操作 |
| **内容安全** | 用户输入和 AI 输出都需内容审核过滤 | ⬜ 未接入 |
| **AI 标注** | AI 生成内容必须标注"由 AI 生成" | ⬜ 未设计 |
| **隐私协议 + 用户协议** | 必须有完整的法律文本 | ⬜ 未准备 |

**关键路径：** 算法备案如果走自研路径需要 45-60 天。本项目调用 DeepSeek API，可走"第三方技术"路径，但仍需获取 DeepSeek 的备案证明 + 使用协议。

**影响：** 如果到 W5 才发现审核门槛，可能错过高考季。

**建议：** W3 同步开始准备审核材料，特别是算法备案和内容安全接入。

#### 3. 「张雪峰」IP 侵权风险

**问题：** 产品名称"峰哥报考参谋"、智能体人设模仿张雪峰说话风格，但 **没有获得张雪峰本人或其公司（峰学蔚来）的授权**。

**风险点：**
- 姓名权：使用"峰哥"暗示与张雪峰有关联
- 不正当竞争：搭张雪峰知名度便车
- 商标风险：张雪峰团队可能已注册相关商标
- 用户混淆：用户可能误以为是张雪峰官方产品

**真实后果：** 一旦被投诉，小程序可能被下架。如果给出错误建议导致用户损失，法律风险更大。

**建议：**
- MVP 阶段改名，避免直接关联（如"AI 志愿参谋"）
- 或者联系张雪峰团队寻求授权合作（如果方向对，这可能是商业模式）
- 在产品中明确标注"AI 模拟风格，非张雪峰本人"

#### 4. 高考时间窗口错过

**问题：** 高考志愿填报的核心窗口只有 **6 月 25 日 → 7 月 5 日**（约 10 天）。错过就等一年。

**时间线反推：**
```
今天: 04/27
目标上线: 05/18（3 周后）
审核周期: 1-3 次 × 3-7 天 = 3-21 天
最坏情况上线: 05/18 + 21 天 = 06/08
缓冲时间: 仅剩 ~17 天做推广和迭代
```

**如果审核被拒 2 次以上，就可能错过高考季。**

**建议：** W3 必须同步准备审核材料，把审核前置。上线日期留出至少 2 周缓冲。

### 🟡 严重级（可能导致产品效果大打折扣）

#### 5. 分数线数据时效性陷阱

**问题：** 当前知识库的分数线是 2023-2025 年数据。但用户在 2026 年 6 月底咨询时，需要的是 **2026 年的分数线**——但 2026 年高考还没考，数据根本不存在。

**用户场景：** "我 2026 年考了 580 分，能上什么学校？"→ 智能体只能基于 2023-2025 年历史数据做推荐，但需要 **明确告知用户这是历史数据参考**，不能当作确切承诺。

**影响：** 如果 AI 把去年的分数线当今年推荐，用户实际录取结果不符，引发投诉。

**建议：**
- 所有分数线回答必须标注数据年份
- 预测功能用"近 3 年趋势"而非单一数字
- 2026 年分数线公布后（~6/25），48 小时内完成数据更新

#### 6. 用户信任鸿沟

**问题：** 志愿填报是影响一生的决策。家长（实际付费者）对 AI 的信任度远低于预期。

**心理分析：**
- 免费对话 → "这东西靠谱吗？" → 用完就走
- 付费报告 → "花 99 块让 AI 帮我填志愿？" → 不如花钱找真人咨询师
- 对比：真人咨询师 2000-10000 元，但家长愿意付

**影响：** 付费转化率可能远低于预期（可能 < 1%）。

**建议：**
- MVP 先验证免费使用的留存和满意度，不急于上付费
- 综合报告的差异化价值要明确（比免费对话多什么？）
- 考虑"AI + 人工"混合模式（AI 出初稿，真人审核）

#### 7. 竞品壁垒极低

**问题：** 这个产品的核心技术（Dify + DeepSeek + 知识库）任何人都能在 1-2 周内复制。真正的壁垒只有数据，但数据来源（掌上高考 API、教育部公开数据）也不是独有的。

**竞品威胁：**
- 掌上高考 APP 自己就有 AI 志愿填报功能
- 夸克高考、百度高考等大厂产品已有成熟方案
- 张雪峰团队的"峰学蔚来"可能自己推出 AI 产品

**影响：** 即使上线成功，也可能被竞品快速淹没。

**建议：**
- 找到差异化定位：不只是 AI 对话，而是"数据深度 + 个性化推荐"
- 建立数据壁垒：专业评估报告的深度和质量是竞品短时间做不到的
- 考虑与高中/机构合作，走 B 端路线避开 C 端红海

### 🟠 注意级（不会致命，但需要提前规划）

#### 8. 一人单点故障

**问题：** 整个项目一个人开发 + 运营。生病、倦怠、或其他工作冲突 = 项目停摆。

**建议：** 关键节点有备选方案（如审核期间可以同时做其他模块）。

#### 9. DeepSeek API 稳定性

**问题：** DeepSeek 过去有过多次服务中断。高考填报高峰期（6 月底）如果 DeepSeek 宕机，整个产品瘫痪。

**建议：** Dify 配置多模型 fallback（主：DeepSeek → 备：通义千问 → 备：智谱 GLM）。

#### 10. 小语种专业数据质量

**问题：** 剩余 193 条中有 30+ 种小语种（桑戈语、豪萨语、茨瓦纳语等）。这些专业公开信息极少，AI 生成报告质量可能很差（甚至编造内容）。

**建议：** 小语种统一归为"外国语言文学类"一条通用报告，不必逐个展开。

#### 11. 高考政策动态变化

**问题：** 各省新高考改革进度不同，选科要求每年可能调整。知识库中的选科信息可能过时。

**建议：** 在回答中加入"请以本省考试院最新公布为准"的免责声明。

#### 12. 家长 vs 学生：付费者和使用者不是同一人

**问题：** 学生用免费对话，家长决定是否付费。两者的需求和决策逻辑完全不同。

- 学生关心：这个 AI 好不好玩、能不能回答我的问题
- 家长关心：靠不靠谱、有没有真人背书、出了问题找谁

**影响：** 如果产品只针对学生设计，付费转化会更低。

**建议：** 综合报告的设计要面向家长（专业、权威、有数据支撑），而非学生。
