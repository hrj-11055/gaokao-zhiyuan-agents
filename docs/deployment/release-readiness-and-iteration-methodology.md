# 上线纠错与版本迭代方法论

更新日期：2026-05-30

本文用于每次准备上线、提审或做大版本迭代前复盘。它不是功能愿望清单，而是一张“能不能把用户带到稳定结果”的检查表。

## 当前上线判断

如果今天立刻上线，可以做小范围体验版或种子用户灰度，但不建议直接大范围正式发布。

原因不是单点功能完全不可用，而是仍有几个上线级风险没有闭环：

- 自动化回归没有全绿：`python3 -m unittest discover tests` 当前 126 个测试中有 5 个失败。
- 正式价格 19.9 元配置已恢复，但仍缺少真机 19.9 元完整复测记录。
- 邀请 5 人解锁、会员邀请码核销、深度 PDF 下载次数扣减仍缺少真机全链路验收。
- 报告生成与 PDF 样张质量需要按正式用户场景抽样，不应只用接口健康判断。
- 支付成功但回调延迟、回调重复、用户取消支付、订单异常补偿这些运营场景还缺少可重复演练。

## 本次审计证据

已验证通过：

- `npm run build:mp-weixin` 构建通过，只有 Sass legacy API 警告。
- 会员、支付、邀请码相关契约测试通过：`tests/test_commerce_store.py`、`tests/test_membership_server_contracts.py`、`tests/test_membership_miniprogram_contracts.py`、`tests/test_vip_code_manager.py`、`tests/test_membership_pages.py`。
- 后端核心文件语法检查通过：`gaokao-proxy/server.js`、`gaokao-proxy/lib/wechat-pay.js`、`gaokao-proxy/lib/commerce-store.js`。
- 线上健康检查通过：`https://gaokao.aicoming.cn/api/health` 返回 `{"status":"ok"}`。
- 报告库健康检查通过：`/api/reports/health` 返回 Postgres connected，且有专业与院校数据。
- 线上支付配置存在：微信 AppID、商户号、证书序列号、商户私钥、微信支付公钥、API v3 key、notify URL、价格 `1990` 分。
- 未登录调用 `/api/payment/create` 会被拒绝，支付接口鉴权生效。
- 无签名调用 `/api/payment/wechat/notify` 会被拒绝，回调验签保护生效。

当前失败或待验：

- `test_chat_page_blocks_input_until_core_profile_is_complete`：聊天页现在缺少 `isProfileReady` 门槛，资料不完整时仍可能进入输入态。
- `test_candidate_questions_are_anchored_below_ai_replies`：候选问题展示没有绑定资料完成状态，和既有产品契约漂移。
- `test_miniprogram_syncs_profile_to_backend`：首页资料同步调用从契约期望的 `profile.value` 漂移为其它对象，需要确认这是有意调整还是回归。
- `test_questionnaire_completion_threshold_is_21_after_question_removal`：首页未显式引用 `QUESTIONNAIRE_REQUIRED_COUNT` 与 `已答 x / 21` 文案，问卷完成阈值表现存在漂移。
- 完整测试里的内容生成质检用例会暴露报告质量风险：当模型或扩写链路输出过短、缺少模块或表格时，应视为内容生产链路需要继续守护。

## 全栈工程师视角

### P0 上线阻塞

1. 自动化测试必须全绿，或者明确废弃并更新过时测试。

当前测试失败集中在用户关键路径：资料完成门槛、AI 咨询候选问题、问卷完成阈值。它们不是无关单元测试，而是影响“用户能否按正确顺序完成档案 -> 咨询 -> 测评 -> 报告”的流程契约。

2. 19.9 元真实支付必须真机复测。

已经验证过 1 元支付，线上配置也已恢复 19.9 元；但正式金额会影响用户信任、商户账单、订单金额校验和客服处理。上线前必须用新测试账号跑完：下单、拉起微信支付、支付成功、回调解锁、会员态刷新、报告生成。

3. 支付异常需要演练。

至少覆盖：用户取消支付、支付成功但前端没有立即查到 paid、重复点击支付、重复回调、金额不一致、会员已开通后再次点击、客服手工核对订单。

4. 生产配置默认值要收紧。

代码中存在对本地开发友好的默认值，例如 session secret fallback、限免入口默认开启逻辑、PDF 下载依赖构建开关。这些适合开发，但生产应当显式配置和启动时校验，避免一次漏配导致权限或支付行为异常。

5. 运营排障能力不够完整。

当前主要靠日志和 SQLite 数据排查。正式上线至少需要一套手工可执行的订单/会员查询命令，能按用户 ID、openid、订单号、商户单号查到状态，并有补开会员或发放补偿邀请码的 SOP。

### P1 稳定性与体验

- 报告生成需要队列化或持久化任务状态。当前已有预生成能力，但要确认重启、超时、失败重试后的用户体验。
- PDF 下载配额要做幂等保护，避免用户重复点击或网络重试多扣次数。
- 小程序端应移除面向开发的 `console.log`，或统一用可开关日志。
- 报告页支付失败目前多为 toast，建议统一到“支付失败 -> 查看原因 -> 联系客服”的路径。
- 需要定期备份会员/订单 SQLite 数据，并写入恢复演练步骤。

### P2 工程质量

- 建立真机验收脚本记录模板，把每次体验版的账号、时间、订单号、报告 URL、PDF 样张记录下来。
- 为 `/api/payment/create`、`/api/payment/order/:orderId`、`/api/report/generate`、`/api/reports/deep/pdf` 增加结构化日志字段。
- 增加线上 canary：每 5 分钟检查 health、reports health、Nginx HTTPS、Dify/score-api 依赖。

## 产品经理视角

### P0 上线前必须确认的用户价值

1. 用户付费后能稳定拿到“他认为值 19.9 元”的结果。

产品不是支付成功就结束，用户真正买的是报告、学校/专业判断、风险提醒和下一步行动。上线前应抽样检查至少 10 个典型画像：高分、中分、压线、物理、历史、广东本省、外省、偏工科、偏文科、家庭预算敏感。

2. 首页任务链路要足够清楚。

用户需要理解为什么要完成四步，以及每一步完成后下一步在哪里。任何“完成了但按钮仍像未完成”“资料没填也能问”“报告入口和测评入口混淆”都会拉低转化。

3. 付费权益表达要具体。

“VIP”本身不说明价值。更适合表达为：完整志愿报告、院校/专业深度阅读、PDF 下载额度、支付后客服兜底。价格、权益、限制和退款/异常处理口径应一致。

4. 邀请 5 人解锁规则要讲清楚。

用户必须知道“新用户 + 完成基础资料”才算有效邀请。否则会产生大量客服问题：“我明明邀请了，为什么没解锁？”

5. 信任感比视觉更重要。

高考志愿是高风险决策，用户会在意来源、免责声明、官方信息核对、报告生成时间、隐私处理、客服能否找到人。版本迭代应优先补信任闭环，而不是继续堆装饰性 UI。

### P1 产品迭代重点

- 报告质量：减少泛泛而谈，增加“为什么推荐、风险是什么、下一步查什么、哪些不能赌”。
- 付费转化：在用户看到足够价值后再开通，不要过早打断。
- 客服闭环：我的页、支付失败、报告失败、PDF 失败都能一键找到客服。
- 分享裂变：邀请页要显示进度、规则、有效邀请列表或至少状态说明。
- 内容合规：所有报告页和 AI 回答要持续提示“仅供参考，最终以官方招生信息为准”。

## 下一版本迭代优先级

### V1.0.1：上线补漏版

目标：让现有 MVP 可被小范围付费用户稳定使用。

- 修复或更新当前 5 个失败测试。
- 真机跑通 19.9 元支付、会员解锁、报告生成、PDF 下载。
- 真机跑通邀请码兑换和邀请 5 人解锁。
- 增加订单/会员客服查询与补偿 SOP。
- 抽样 10 份综合报告、5 份学校深度报告、5 份专业深度报告。

### V1.1：信任与转化版

目标：让用户更清楚为什么值得付费，并能放心使用。

- 增加权益说明页或支付前确认页。
- 增加邀请进度说明和规则提示。
- 支付/报告/PDF 失败统一接入客服入口。
- 记录核心漏斗：进入首页、保存资料、完成咨询、完成测评、点击支付、支付成功、报告生成、PDF 下载。
- 优化报告结构，把风险、依据、行动建议前置。

### V1.2：运营与规模版

目标：减少人工排障，提高稳定性。

- 报告生成任务持久化，支持断点、重试、状态查询。
- 订单、会员、邀请码后台管理或命令行工具完善。
- 增加线上告警和定期备份。
- 建立“黄金用户画像”回归集，每次模型、提示词或数据变更后跑样张对比。

## 每次迭代的方法论

### 1. 先定义版本目标

每个版本只回答一个问题：

- 这是上线补漏、转化提升、内容质量、运营提效，还是技术偿债？
- 这个版本不做什么？
- 成功指标是什么？

不要用“做完很多功能”定义版本，用“用户完成了什么结果”定义版本。

### 2. 画关键用户旅程

每个版本至少检查这些旅程：

- 新用户：进入首页 -> 填资料 -> AI 咨询 -> 两项测评（性格类型定位 + 霍兰德职业兴趣）-> 开通会员 -> 生成报告。
- 付费用户：支付 -> 会员解锁 -> 报告生成 -> 在线阅读 -> PDF 下载。
- 免费解锁用户：被邀请 -> 完成资料 -> 邀请人进度增加 -> 满 5 人解锁。
- 客服异常：支付成功未解锁 -> 用户提供材料 -> 后台核对 -> 补开或解释。

任何旅程中断，都比一个孤立页面不好看更重要。

### 3. 给每个功能写验收标准

每个功能至少要有四类验收：

- 前端验收：页面能进入、状态正确、错误提示可理解。
- 后端验收：接口鉴权、数据写入、幂等、错误码稳定。
- 真机验收：在微信开发者工具和真实手机上都跑通。
- 运营验收：客服知道用户失败后该看什么、问什么、怎么补偿。

### 4. 每次上线走四道门

第一道门：自动化。

```bash
python3 -m unittest discover tests
cd gaokao-miniprogram && npm run build:mp-weixin
node --check gaokao-proxy/server.js
node --check gaokao-proxy/lib/wechat-pay.js
node --check gaokao-proxy/lib/commerce-store.js
```

第二道门：线上健康。

```bash
curl -s https://gaokao.aicoming.cn/api/health
curl -s https://gaokao.aicoming.cn/api/reports/health
curl -s -X POST https://gaokao.aicoming.cn/api/payment/create
```

第三道门：真机关键路径。

- 新账号 19.9 元支付。
- 支付成功后会员自动解锁。
- 生成综合报告。
- 打开在线报告。
- 下载综合 PDF 和深度 PDF。
- 兑换邀请码。
- 邀请 5 个新用户解锁。

第四道门：运营兜底。

- 客服微信入口可见。
- 用户 ID 可复制或截图。
- 后台能查订单和会员。
- 支付失败和报告失败有明确话术。
- 当天发布后有人看日志。

### 5. 用风险而不是喜好排序

排序公式：

```text
优先级 = 用户影响面 x 损失严重度 x 发生概率 / 修复成本
```

支付失败、报告拿不到、会员不解锁、资料丢失、错误推荐，永远优先于视觉细节。视觉可以影响转化，但关键链路坏了会直接造成退款、投诉和信任损失。

### 6. 灰度发布

正式发布前至少经过：

- 内部测试账号。
- 3 到 5 个种子用户。
- 20 到 50 个小范围用户。
- 再考虑大范围发布。

每一阶段都要记录：支付成功率、报告生成成功率、客服问题类型、用户是否看懂下一步。

### 7. 复盘只看事实

每次迭代结束，记录：

- 做了什么。
- 哪些测试通过。
- 哪些测试失败。
- 哪些真机路径通过。
- 用户最常见卡点。
- 下一版只解决哪 3 个最重要问题。

不要只记录“感觉好很多”。上线系统需要证据，不需要自我安慰。
